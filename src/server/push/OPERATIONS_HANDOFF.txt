Bloom operational notifications — local implementation, 2026-11-07

2026-11-08: native enrollment and dual delivery are implemented locally through
migration 084. See NATIVE_DELIVERY_RUNBOOK.txt for actual service evidence,
remaining physical acceptance, HTTPS configuration and scheduler release steps.

Existing services retained

OneSignal transport, physical-device/account links, Clerk auth, account master,
category preservation, dispatch leases/idempotency keys, authorized alert-open
routing, report storage, confirmed external-payment ledger, manual calendar,
calendar sync leases/provenance and the existing evening/morning summaries.
No hosted migration, broadcast, transport replacement or production activation.
New-device ownership-proof registration remains an outstanding dependency.

Migrations

079: decline-safe private default assignment; comment-required decline endpoint;
assignment schedule revision; confirmed imported/manual guest stay extensions
move the same unstarted job, retaining assignment and reservation identity.
Only selected defaults are assigned, within snapshotted capacity. A withdrawal
history record prevents any later automatic replacement/default retry for that
job. Explicit owner staffing remains available. No on-call replacement.

A confirmed imported extension requires the same source event, confirmed
reservation evidence, unchanged check-in, later checkout, a single provenance
link, no manual-return ambiguity, no competing checkout and an unstarted,
uncompleted, unheld job. Other changes stay on review. Manual reservation edits
carry explicit extension intent; arbitrary manual cleaning moves do not count.
The decline exception applies only to private assignments or an assignment
predating the job's current guest-extension revision. Started work is rejected.

080: grouped account categories plus a private event ledger shared by inbox and
push. Assignment, teammate, withdrawal, changed-job, payment, compensation,
coverage, invitation, request and calendar-error triggers use current scope.
Dispatch recomputes authorization, assignments, live job state and category
preference. The existing account master suppresses queued work across devices.
Inbox generation is independent of account push preferences.

Expected compensation uses the job snapshot: Bloom total divided by actual
participants; private equal split with deterministic penny allocation; explicit
private amounts remain unchanged. Adjustments have separate copy. Only the
committed external-payment entry emits "sent you"; earning/completion alone
never claims money was sent. Voided entries stop producing payment content.

Assignment-event recipient uniqueness covers an admin who also participates;
hub switching is not another account. Own claim/completion confirmations are
suppressed. Existing scope currently gives Bloom admins global property access;
routing reuses people_access rather than inventing an assigned administrator.
Private staffing goes to authorized owners, including an admin explicitly
listed as a property owner, not every globally authorized admin.

New-job import batching stays in the existing publisher. Unclaimed opportunity
reminders require zero current assignments and a currently claimable, unstarted
Bloom-managed job; pool opt-in, approval and approved city are rechecked. A
recipient/job/property-local-day ledger deduplicates overlapping opportunities.
Same-day creation, release from hold/setup, and zero-staff withdrawal emit an
immediate coverage event; the pool never receives private work. Coverage events
share a revision/day key, so a scheduled check does not duplicate an opening,
while a later zero-staff withdrawal creates a new coverage episode.

Supply/maintenance report provenance is retained. Issue episodes suppress
unchanged findings on later completions. Resolution and a later recurrence can
start a new episode. Current restock/report state is checked at dispatch.

Scheduling and actual activation

Existing upcoming-cleaning summaries: 18:00 evening before, 08:00 morning of,
using the configured city notification timezone and current assignments.
New unclaimed/coverage checks: 08:00 property-local, for cleaning dates +3 and
+1 (plus same-day manager coverage). Reminder retry windows last one hour;
there is no late catch-up blast. Payer summaries default to Monday 09:00 in the
payer's configured city timezone (Detroit fallback). No per-completion payout
reminder push is emitted. These defaults are code-side scheduling policy.

Operational delivery requires an authenticated caller of POST /api/push/tick,
a valid BLOOM_PUSH_SCHEDULER_SECRET, explicitly configured delivery mode and
provider credentials, activation, and proven device registration. None is
implicitly enabled by a migration or by the preference switch. The local
preview inspected before migrations had push mode off, no scheduler secret,
no OneSignal configuration, activated=false, lastTickAt=null, and zero verified
devices. No automatic push scheduler process or repository deployment cron was
found. Timed delivery is NOT operational in this environment.

A coverage event is recorded immediately in the same transaction. Physical
push still depends on the configured sender's next dispatch and registration;
there is no promise of immediate OS receipt while those dependencies are off.

Frontend

Settings remain in the bell dropdown. The standalone prompt disappears when
account push is on. A divider separates the master from categories. Off shows
all categories off/inactive while preserving choices for re-enable. Device
settings stay collapsed; errors/retry are action-local there. No verification
push/resend UI is restored. Private or moved assignments offer "Decline job"
with a required comment, keeping completion controls separate from decline.

locks reversed the existing calendar property→job order. Claim eligibility
uses NO KEY UPDATE for non-key user changes, preserving serialization without

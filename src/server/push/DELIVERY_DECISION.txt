DECISION

New-device registration remains BLOCKED on the present OneSignal Web transport.
Recommend standards-based Web Push using Bloom-owned VAPID keys, preserving the
existing account preferences, device/account links, outbox and authorized opens.
This is a concrete replacement proposal, not a provider change. No sender, SDK,
worker, hosted database, production activation or credentials were changed here.

Why the supported OneSignal paths do not meet the requirements:

1. Official Identity Verification documentation says Web SDK signed identity
   verification is unsupported. Enabling app-wide enforcement causes Web user
   and subscription creation/update to fail. A signed Bloom account JWT cannot
   currently secure the supported Web enrollment flow.
   https://documentation.onesignal.com/docs/en/identity-verification
2. The subscription guide explicitly excludes creating Web Push subscriptions
   through REST. The generic create-subscription schema is NOT a supported
   server-enrollment solution for Web, even though it lists web key fields.
   https://documentation.onesignal.com/docs/en/subscriptions
3. Existence/alias lookup is not ownership proof. Comparing provider-returned
   endpoint/key fields has no established immutable ownership attestation:
   the SDK updates and transfers subscriptions using public application and
   subscription identifiers. Do not adopt an undocumented equality check as
   a security boundary. Display webhooks are browser callbacks and exclude
   Safari, so they do not supply a universal authenticated enrollment proof.
   https://documentation.onesignal.com/docs/en/webhooks
4. Inspected official Web SDK commit:
   fef4d4ea4a5178bf89ebbf0883deaf7ee75858ba
   https://github.com/OneSignal/OneSignal-Website-SDK/tree/fef4d4ea4a5178bf89ebbf0883deaf7ee75858ba
   OneSignal.ts exposes an optional login JWT, but LoginManager only persists
   it. RefreshUserOperationExecutor and SubscriptionOperationExecutor do not
   pass it to the relevant user/subscription requests. An optional argument
   alone does not establish supported enforcement. Recheck official support
   before revisiting this decision; do not turn on native-only enforcement.

The existing receive-and-click challenge is excluded by the product decision.
An arbitrary client-provided subscription ID, external_id or alias is excluded
by the security requirement. Adding an API secret cannot resolve these gaps.

BOUNDED REPLACEMENT IMPLEMENTATION

1. Add a separately reviewed schema migration after 083 (proposed 084; not
   implemented/applied). Extend physical device transport state with active
   transport/generation, encrypted native subscription, endpoint digest unique
   constraint and encryption key version. Keep account links and preference rows.
   RPCs remain service-only. Endpoint/key material never enters logs or ordinary
   diagnostics. Do not falsely label migrated rows as proven OneSignal devices.
2. Use a maintained Web Push implementation for encryption/VAPID, not homemade
   cryptography. Register /bloom-push/worker.js at /bloom-push/ scope; use that
   registration directly for PushManager, leaving the OneSignal scope untouched.
   A PushSubscription contains an endpoint plus secret auth and public p256dh
   material. Treat the complete subscription as a confidential capability, not
   a public provider ID. Validate key sizes/encoding and HTTPS endpoints against
   exact supported push-service hosts; prohibit redirects, local/private address
   targets, embedded credentials and arbitrary URL fetching. Limit request sizes
   and rates. An endpoint alone never authorizes linking or changing any device.
   https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe
3. Prepare the worker before the action. Request native permission synchronously
   from the user's enable gesture when needed, then subscribe and authenticate
   registration automatically. No verification notification or resend UI.
   Use a short-lived, one-use enrollment nonce tied to the HttpOnly server-created
   device capability, authenticated Clerk subject/session, expected account and
   registration generation. Enforce same-origin mutation/CSRF protections.
   Derive the recipient from authentication, never the submitted account ID.
   Reject reused nonces, stale sessions, mismatched accounts and attempts to
   replace another device's endpoint. Never transfer an existing endpoint to a
   different cookie/device on the strength of an ID. Enrollment security relies
   on the secret capability and authenticated origin, not a delivery assertion.
4. Bind the complete subscription to that device and explicitly connect the
   authenticated account in one transaction. Existing devices connect a second
   account only after that account authenticates and explicitly enables/connects.
   Session renewal, logout and hub switching neither add links nor erase links.
   Validate UI results against the starting account/session before applying them.
   Do not require second native permission for the same browser subscription.
5. Preserve the distinction between account push preference and device readiness.
   Master-off suppresses queued account sends across devices and leaves inboxes
   and other account links alone. Registration success means device registered;
   it does not establish delivery. Keep short action-local errors and optional
   test controls. A generic optional test failure must not invalidate the device.
6. Reuse fresh SQL eligibility immediately before sending and before personalized
   display. Preserve /notifications/open intended-account authorization; signing
   into a different account cannot expose the destination. Recheck job/property
   permissions after sign-in, including revoked assignments and property access.
7. Switch exactly one active transport per device under the device/dispatch lock.
   Wait for any existing send lease to resolve before switching generations.
   Retain logical delivery IDs and terminal records. Reconcile pending attempts;
   never replay accepted/expired/skipped history into a new transport. Keep proven
   OneSignal devices usable until explicit native enrollment. Do not assume the
   OneSignal VAPID private key is exportable; permission may be reused, but a new
   Bloom-owned subscription requires explicit enrollment.
8. Direct Web Push has no universal provider idempotency API. Use stable delivery
   UUIDs, leases, bounded retries, notification tags and a persistent worker receipt
   ledger to suppress repeats. Test ambiguous send/commit failures explicitly;
   exactly-once external delivery cannot be promised. Rollback uses the same
   single-active-transport gate, never parallel fan-out or historical replay.
   HTTP 404/410 disables the native subscription, not account preferences;
   429/temporary failures retry with bounds and concise action-local feedback.
9. Before ANY acceptance send, implement a second test restriction by device:
   BLOOM_PUSH_TEST_DEVICE_IDS AND BLOOM_PUSH_TEST_SUBJECTS must both match.
   Current code checks only subjects. The device guard is proposed, not working
   configuration today. Test endpoint must dispatch only its specific delivery;
   scheduler acceptance must run against an isolated database with synthetic data.
10. Retire challenge routes/state and verification page only after real enrollment,
    migration/rollback, expired-state cleanup and all acceptance checks pass.
    Do not revive the obsolete interaction while this work is pending.

SCHEDULER INSPECTION, ACTIVATION AND ROLLBACK

Actual endpoint: authenticated POST /api/push/tick, maxDuration 60 seconds,
Bearer BLOOM_PUSH_SCHEDULER_SECRET (at least 32 characters). GET is not a tick.
It calls bloom_push_tick then dispatches at most five leased deliveries per
request. Missing/off BLOOM_PUSH_MODE prevents sending. Current local mode is
absent/off and there is no local cron installation or heartbeat.

Existing release mechanism: supabase/push/enable-schedule.sql installs pg_cron
and pg_net, calls bloom_push_activate and schedules bloom-push-delivery every
minute using net.http_post with a 55-second timeout and Vault lookups. It is
hard-coded to the production origin. DO NOT execute it for local/staging tests.
Older supabase/push/HANDOFF.txt contains contradictory historical production
snapshots; none establishes today's hosted state. No hosted query was made here.

Current timing from SQL: assignment summaries at 18:00/08:00 in configured city
timezone; zero-cleaner three/one-day opportunities at 08:00 property-local;
payer summaries Monday 09:00 configured payer timezone (Detroit fallback).
Timers tolerate a one-hour window, not arbitrary late catch-up. Same-day coverage
events are emitted by job/withdrawal triggers, with sender latency up to a tick.

Exact release sequence, only AFTER replacement and device restrictions pass:
1. In the intended isolated test database inspect migration ledger, activation,
   health, cron.job existence/status and recent HTTP responses without displaying
   Vault decrypted values or cron credentials. Set mode test with BOTH allowlists.
   Stop if the database includes real recipients/jobs, registration is unavailable
   or a required key is absent. Save activation/schedule metadata privately.
2. Configure Vault names bloom_push_url and bloom_push_scheduler_secret; the latter
   must match BLOOM_PUSH_SCHEDULER_SECRET. Use a reviewed STAGING copy of the SQL
   with an exact staging-origin guard, retaining its secret/count checks. Never
   weaken or retarget the committed production guard for convenience.
3. Within that explicit release run, in order:
     create extension if not exists pg_cron;
     create extension if not exists pg_net;
     select public.bloom_push_activate();
     select cron.schedule('bloom-push-delivery','* * * * *',$job$
       select net.http_post(
         url:=(select decrypted_secret from vault.decrypted_secrets where name='bloom_push_url'),
         headers:=jsonb_build_object('Content-Type','application/json','Authorization','Bearer '||(select decrypted_secret from vault.decrypted_secrets where name='bloom_push_scheduler_secret')),
         body:='{}'::jsonb,timeout_milliseconds:=55000);
     $job$);
   Activation baselines historical publications; it is not a schema prerequisite.
4. Confirm a recent health heartbeat and HTTP 200 through both cron run details
   and pg_net response status. A successful cron SQL job alone does not prove
   the HTTP request authenticated. Then run only designated synthetic acceptance.
   Never dump Vault, request headers or response bodies containing private data.
5. Production requires a separate explicit release after physical acceptance;
   it is not implied by applying migrations or completing this local task.

Exact rollback/pause on the deliberately activated target:

    where jobname='bloom-push-delivery';
  begin;
  select pg_advisory_xact_lock(hashtextextended('bloom-push-tick',0));
  update private.push_control set activated_at=null where singleton=true;
  commit;

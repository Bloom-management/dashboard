CURRENT IMPLEMENTATION

applied through the guarded local migration process. The local preview remains
http://localhost:3000 on main; existing uncommitted work was preserved.

Native enrollment: explicit enable -> native permission when needed -> browser
PushManager subscription -> authenticated nonce -> encrypted server registration
and explicit account/device link. No verification notification or resend step.
The permission/subscription chain starts inside the gesture, before awaiting the
preference save. The worker is prepared without prompting or linking accounts.
Registration means readiness, never confirmed receipt. The legacy verified DB
column is reused as readiness; it does not attest native delivery.

Current local sending mode is test, restricted by BOTH Clerk subject and hashed
device allowlists to cleanertest/ownertest and their designated preview profiles.
The admin preview is not a push recipient. Background delivery remains inactive,
with no scheduler heartbeat/cron installation. Optional tests dispatch only their
one delivery even with background activation off. No broadcasts, hosted changes,
real job-date edits or production activation occurred.

Account preference/category/inbox services and operational notification SQL are
retained. Logout and hub/account switching do not enroll or disconnect accounts.
Unlink affects only the viewed account. It never unsubscribes the shared browser
subscription needed by other accounts. Native browser permission/subscription
presence is displayed separately from the account master. Expiry does not switch
off that master. Browser permission must still be allowed by the actual user.

SECURITY GUARANTEES AND LIMITATIONS

Enrollment authenticates Clerk, derives the actor server-side, checks expected
account AND session, and uses a server-created HttpOnly device capability. Its
one-use nonce is hashed, expires after five minutes, and is bound to that actor,
session, device and registration generation. Same-origin/CSRF, bounded body/key
validation and a short enrollment retry limit apply. Device IDs supplied in a
body are not accepted. An endpoint cannot transfer an existing device or its
account links to another cookie/device. Role/scope comes from existing services.

The full native subscription is validated (vendor-operated HTTPS origin,
endpoint shape, valid curve point and auth secret), then sealed using AES-256-GCM.
No endpoints, auth keys, encryption keys or cookies are exposed in diagnostics.
No arbitrary outbound URL/redirect is followed. Unsupported vendor origins fail
closed; extend the allowlist only after checking the vendor's official format.

IMPORTANT: a syntactically valid subscription is not an attestation that its
submitter controls the receiving browser. This is why registration alone cannot
grant content access. A caller can fabricate subscription fields; that only
creates their OWN authenticated link, never another account's device identity.

For native content fetch, dispatch installs a per-delivery secret hash in SQL.
The secret is stable across retries and is sent ONLY inside the encrypted push
payload. Enrollment/test responses never reveal it. /api/push/display requires:
  1. the receiving browser's HttpOnly device capability;
  2. that exact delivery's received secret;
  3. its enabled account/device link and eligible delivery state;
  4. current category, property/job/assignment authorization and expiry checks.
An endpoint, account ID or delivery ID alone cannot retrieve another account's
content. Display responses contain current content and the account-check URL,
never subscription credentials. Private content is absent from vendor payloads.
Legacy proven OneSignal deliveries retain their existing capability check.

Notification display intentionally works after logout for explicitly connected
accounts. This is a trusted-browser capability, not an application login. The
alert-open page separately requires the intended authenticated account and fresh
destination authorization. Device notification content can be visible on a lock
screen or to another person using that same trusted browser. Same-origin XSS,
compromised device cookies/server secrets and OS-level compromise are outside
these guarantees. The encrypted delivery secret prevents endpoint/identifier-only
enrollment from becoming a content-fetch credential; it does not replace XSS
prevention or the application's normal authorization.

Only confirmed provider 404/410 invalidates native registration. Network errors,
429 and 5xx retry with the existing bounded leases/backoff; generic test failure
does not disable it. Local expired subscription input is rejected at enrollment.
If cookies are cleared while a browser retains its old subscription, endpoint
transfer is deliberately refused. Reset Bloom's site notification/site data and
enable the device again; authenticate each account whose connection was lost.
Do not silently copy old account links onto a new device cookie.

The native vendor protocol has no universal idempotency API. Logical message/
device identity is serialized across generations; migration never replays accepted
or previously attempted messages. Stable IDs/topics/tags and a persistent worker
receipt ledger suppress retries/restarts. A crash between OS display and receipt
commit, storage eviction, or ambiguous vendor acceptance cannot provide a strict
exactly-once guarantee. The receipt ledger is best effort and stores IDs, not
private content. Already handed-off/displayed alerts cannot be retracted.

EXISTING ONESIGNAL DEVICES / ROLLBACK

Existing proven OneSignal rows and account links remain usable through the legacy
sender. No one is silently unsubscribed or moved merely by visiting settings.
To move a browser, the user clicks Update this device under Device settings once.
The same native permission can generally be reused; a Bloom-owned subscription
is necessary because OneSignal's VAPID private key is not assumed exportable.
The account master and saved category choices remain unchanged. Users do NOT
need to toggle their account preference off/on or redo setup on every hub switch.
Each browser/Home Screen installation needs its own one-time migration action.

Switching is atomic, refuses a live send lease, preserves all links, and allows
one active transport only. Unsent pending deliveries keep their UUID. Accepted
history and ambiguous attempted sends are never replayed across the switch.
Rolling back a migrated proven device uses this service-only operation after
pausing/draining the sender:
  select public.bloom_push_rollback_device(:'device_id');
It restores only the retained proven OneSignal registration and maps unsent
pending work back under a new generation. Retain the OneSignal worker and keys.
Native-only devices have no proven OneSignal fallback; the RPC fails closed.
Keep the dual-capable code and repair native delivery, or pause that device's
delivery. Never manufacture a proven legacy registration or erase its preferences.

The sealed subscription format is v1 with authenticated encryption. Preserve the
encryption key. Key rotation requires an explicit re-encryption/key-version
migration; replacing it in the environment alone would strand stored endpoints.
VAPID rotation likewise needs explicit browser re-enrollment and a phased release.

PHONE ACCEPTANCE STEPS

1. Open the selected HTTPS test origin and sign in using the existing development
   cleanertest credentials. A phone cannot use this Mac's localhost URL. On iPhone
   add Bloom to Home Screen, open its icon, then sign in there; Safari alone is
   not the installed app. Android Chrome can be tested directly and installed.
2. Before allowing sends, explicitly designate/approve this phone's device ID.
   Opening settings creates only an unlinked device row. On the isolated test DB
   inspect its new row with the test account/time and approve that exact hashed
   ID in BLOOM_PUSH_TEST_DEVICE_IDS; preserve prior designated test IDs. Do not
   put the raw cookie, endpoint or encryption keys into the allowlist. Redeploy
   the test environment with that server-only change. Inspect ambiguous multiple
   candidates instead of approving every device belonging to an account.
   Safe inspection on the isolated two-account test database:
     select u.display_name,d.id,d.updated_at,d.transport,d.verified
     from private.push_devices d join public.users u on u.id=d.user_id
     where u.display_name in ('cleanertest','ownertest')
     order by d.updated_at desc;
   The returned ID is a hash, not the device cookie. Do not export private
   subscription columns, decrypted Vault secrets or the raw cookie.
3. Bell -> settings gear -> Enable push notifications. Allow the actual native
   prompt. If the account master is already on, expand Device settings and select
   Enable on this device. Enrollment should finish automatically. No verification
   push/click and no "delivery confirmed" claim. Capture OS/browser/version.
4. Use Send test notification once. Independently observe the actual OS alert,
   background/lock the phone and repeat when permitted, then tap it. Record
   delivery UUID, provider acceptance, OS receipt time and the authorized target
   separately. Browser getNotifications is insufficient physical receipt evidence.
5. In that SAME installation authenticate ownertest, explicitly enable/connect,
   and repeat one individual test. Sign out/switch between the two accounts; open
   an alert with the wrong account active and require the correct sign-in/switch.
6. Turn Cleaner master off. Confirm its inbox/unread remain and Owner still
   receives its individual test. Use a second explicitly approved device to check
   account-wide suppression. Restore intended test preferences afterward.
7. Run synthetic due-reminder SQL acceptance locally as above. For an actual
   timed phone test create ONLY labeled synthetic jobs in the isolated test DB;
   never alter real job dates. Exercise expiry and changed assignment/opt-in before
   dispatch, then repeat ticks and check logical IDs for deduplication. Do not add
   a client-controlled clock override to the production endpoint.

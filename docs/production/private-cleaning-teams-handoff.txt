What is implemented
- Existing properties remain Bloom-managed. New owner-created listings are private,
  with the creating owner fixed as payer. Adding a co-owner does not change that payer.
- Property settings offer "Bloom is managing the cleaning", pending approval,
  defaults, capacity (1–20), total/individual compensation, and property-only invitations.
  Supported, previously approved properties can activate service immediately.
  Pending requests remain private; per-turnover coverage has an explicit admin review.
  Property-default changes do not rewrite existing job commitments or completed earnings.
- Verified Clerk identities accept trusted property invitations. New private cleaners
  see the existing welcome dialog with Bloom participation off; existing cleaners
  accept without repeating account onboarding. Incompatible roles are rejected.
  Owners can invite during onboarding or after successful listing creation; retries
  retain the listing and invitation operation identity.
- Network participation is independent of property membership. Opting out hides
  public discovery/new-job alerts but retains accepted Bloom jobs and private work.
- Default cleaners are assigned once; there is no automatic rotation. Membership
  removal flags outstanding work. Private withdrawal requires a comment without
  Bloom's six-hour restriction. Owners review vacancies and assign replacements.
- Existing start/photos/instructions/supplies/maintenance/completion experience is
  reused. Job headers identify responsible team and payer.
- Integer, deterministic completion earnings freeze agreed pricing. Equal $90
  becomes $45/$45 or $90 for the sole remaining participant. Individual agreements
  do not increase automatically; documented adjustments are available.
- Owner Payouts reuses the ledger: completed jobs, adjustments, partial external
  payments, references, and audited void/correction. Cleaner earnings are grouped
  by payer; owner obligations never become Bloom obligations.
- Inbox integrates invitation, staffing, assignment and management duties, using
  current state so resolved work disappears. Existing dismissals remain supported.
  Private jobs do not generate public city-wide discovery pushes.

- Vercel can promote the preceding deployment, but older UI is not a complete
  functional rollback for newly created private work. Pause new listing/onboarding
  writes while assessing compatibility and keep private data inaccessible publicly.
- Do NOT drop the new tables/columns, mark private jobs public, or rewrite payer
  snapshots to make old code run.
- A database restore requires a reviewed backup/recovery plan and paused writes;
  preserve/reconcile every post-release earning/payment before restoring. There is
  no safe automatic destructive down migration for financial history.

Operational dependencies and limits
- Existing Clerk delivery configuration is required; acceptance used development
  test identities only. No real cleaners were invited.
- Scheduled pushes remain inactive. Recurring sync and reminder delivery need their
  existing hosted scheduler/queue configured and independently verified.
- Private properties outside Bloom service areas can use registered inactive cities.
  Admins must register an unlisted city and its verified notification timezone;
  this does not activate Bloom service. Private access does not require network eligibility.
- Individual default amounts must be entered for all selected defaults or all left
  blank for equal sharing. Mixed pricing is rejected explicitly.
- Bloom records external payments and host charges; it neither transfers money nor
  charges owners in this implementation.
- No additional paid provider or new secret is introduced by this feature.
